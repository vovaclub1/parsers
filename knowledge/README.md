# База знаний: Listings / Delistings Trading

Эта папка — рабочая база знаний проекта. Цель не «знать больше о трейдинге»,
а системно превращать знания в проверяемые гипотезы, код, метрики и решения.

## Главный вывод

Текущий проект уже неплохо решает задачу **быстро получить сигнал и отправить
ордер**. Это необходимо, но недостаточно для прибыли.

Прибыльность определяется цепочкой:

```
ожидаемая прибыль = информационный edge
                    - опоздание сигнала
                    - spread
                    - slippage
                    - market impact
                    - комиссии
                    - funding
                    - adverse selection
                    - ошибки исполнения
                    - хвостовой риск
```

Мы сейчас измеряем в основном задержку до `ws.send()`. Это техническая
метрика, не экономический результат. Frame на проводе не означает fill,
а локальная цена из кеша не означает цену исполнения.

## Правила работы

### 1. Факты отделяются от гипотез

- **Факт:** Bybit подтверждает fill с ценой и комиссией в execution stream.
- **Факт:** в коде сейчас нет постоянного event-store сделок.
- **Гипотеза:** листинг Upbit даёт положительный drift на Bybit в первые 5 секунд.
- **Неизвестно:** сохраняется ли drift после taker fee и slippage на нашем размере.

### 2. «Прибыльная стратегия» — только после out-of-sample

Не называем стратегию прибыльной, пока нет:

- минимум 100 независимых событий или достаточного статистического power;
- разделения train / validation / untouched test по времени;
- комиссий, funding, spread и slippage в симуляции;
- bootstrap confidence interval для expectancy;
- walk-forward / purged validation;
- paper/shadow периода с реальным latency и реальным стаканом;
- live canary на минимальном размере.

### 3. Каждый эксперимент регистрируется до запуска

До анализа записываем:

- гипотезу;
- выборку;
- признаки;
- entry / exit;
- размер позиции;
- метрики успеха;
- критерий остановки;
- число уже проверенных вариантов.

Иначе после просмотра результатов легко подогнать параметры задним числом.

### 4. Не оптимизировать наносекунды раньше экономики

Порядок:

1. доказать положительное net expectancy;
2. исключить ложные сигналы и ошибки исполнения;
3. построить корректный risk engine;
4. измерить bottleneck;
5. только потом оптимизировать latency.

### 5. Все боевые решения воспроизводимы

Каждая сделка должна быть восстанавливаема из данных:

- какой источник и payload;
- когда сигнал родился / пришёл / распарсился;
- какой тикер и почему извлечён;
- какой стакан был на входе;
- какой ордер отправили;
- ack / reject / fill;
- фактическая цена и комиссия;
- TP/SL и выход;
- итоговый P&L.
